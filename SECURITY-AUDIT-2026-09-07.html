Critical1 issue · fix today

Could lead to theft of every visitor's personal data, or site-wide disruption.

C1One shared password guards all visitor data, and the site tells attackers when a guess is correct

Problem
GET /api/admin/maintenance needs no login. Send any value in the x-geointel-admin-key header and it replies "adminKeyValid": true or false. I confirmed this live on your site today. That turns guessing the admin password into a simple loop with instant feedback. The same password is the only thing protecting /api/admin/submissions.
Why it matters
A correct guess returns up to 50 feedback rows and 50 team applications, each including the submitter's name, email, message, IP address and browser. It also lets an attacker switch your entire site into maintenance mode for every visitor. There is no lockout, no expiry, no alerting, and no way to tell one admin from another because there is only one password for everyone.
Where
api/_routes/admin/maintenance.ts:63-76 api/_routes/admin/submissions.ts:38-73 api/_lib/rateLimit.ts:78-95
Attack path
Guess against the oracle from a pool of cloud IP addresses, which sidesteps the per-IP limit of 20/minute. The limit also silently falls back to a per-instance memory counter whenever Supabase is slow or erroring, and on Vercel that counter resets on every cold start, so during an outage it is effectively unlimited. Then read every visitor's PII.
Fix
Four changes, in this order:
  • Delete adminKeyValid from the unauthenticated GET. Move verification to a POST /api/admin/verify that returns a bare 200 or 401 and nothing else.
  • Add a global failed-attempt budget, not per IP, so a distributed guess is still bounded.
  • Make the limiter fail closed for the admin scope specifically when Supabase is unreachable.
  • Set a new key of at least 32 random characters. Longer term, put /api/admin/* behind Vercel Access rather than a shared passphrase.
Rotate?
ROTATE GEOINTEL_ADMIN_KEY The oracle has been live on a public site. You cannot prove nobody ground against it, so treat the current key as burned.

H1Your AI endpoint has no working spend limit

Problem
/api/ai-intent uses an in-memory counter (10/min) instead of the durable Postgres limiter. On Vercel that counter is per serverless instance and resets on every cold start, so parallel connections each get a fresh budget. Your other two AI routes were migrated to the durable limiter for exactly this reason; this one was missed.
Why it matters
Anyone can loop requests and burn your OpenRouter quota or bill. Exhausting it also takes down Ask maNOWj and all six agents for real users.
Where
api/_routes/ai-intent.ts:25,120
Fix
const rate = await checkDurableLimit("ai", getClientIp(req), 60_000, 15);
Use the same "ai" scope as copilot and agent so they cannot be alternated for triple budget.
Rotate?
No, unless you see unexplained OpenRouter spend, in which case rotate OPENROUTER_API_KEY.

H2Rate limiting does not actually work on 17 of your 22 endpoints

Problem
Only admin and the two AI routes use the durable Postgres limiter. Everything else uses new RateLimiter(...), which is per-instance memory. Serverless functions do not share memory, so the limit is not a limit.
Why it matters
The reasoning at the time was "the CDN absorbs it", but the CDN only caches repeated URLs. Random coordinates miss the cache every single time, and every miss is a real upstream query to Overpass, Nominatim, Wikidata or OSRM. /api/reverse-geocode is the worst: one request fires up to five sequential Nominatim calls.
Where
api/_lib/cache.ts:40-61 and every new RateLimiter( call site
Attack path
Loop /api/gis?lat=<random>&lon=<random>. Overpass and Nominatim ban datacenter IPs for this. The result is not a data breach, it is your GIS evidence, Nearby, click-to-inspect, Property Intelligence, officials and every AI agent going dark at once.
Fix
Move at least reverse-geocode, geocode, officials, status and the four Overpass routes onto checkDurableLimit, with a generous window (120/min) so ordinary use is unaffected.
Rotate?
No.

H3You are over the Nominatim usage limit, and there is no mechanism that could keep you under it

Problem
The OSM Nominatim policy is an absolute maximum of 1 request per second for your whole application, and results must be cached. Your code has no outbound throttle to Nominatim at all. The 30/min limit is per visitor, not for your app in total, so ten people at once are permitted 5 requests per second. The cache is per serverless instance, so each new instance starts empty.
Why it matters
One person typing a place and picking a result puts roughly 8 Nominatim requests on the wire in about two seconds. The zoom-fallback loop alone fires up to 5 back-to-back calls with no delay between them. Nominatim blocks abusers by IP without notice. If they block Vercel's egress IPs, all search and click-to-inspect stops working.
Where
api/_lib/nominatim.ts (no throttle) api/_routes/reverse-geocode.ts:89-101 src/features/search/SearchBar.tsx:51 (300 ms as-you-type autocomplete, which the policy explicitly asks people not to build)
Fix
  • Collapse the zoom-fallback loop to one request at zoom 18, falling back at most once. That alone removes roughly 60% of your Nominatim traffic.
  • Add a global outbound token bucket of 1 request/second in api/_lib/nominatim.ts, backed by the Postgres limiter you already built.
  • Raise the search debounce to 600 ms and require 3 characters.
  • The real fix is to move geocoding to a provider that permits autocomplete. LocationIQ is Nominatim-compatible, so it is close to a drop-in change, and its free tier is about 5,000 requests/day.
Rotate?
No.

H5Four of your data providers can cut you off, and one is a licensing question

Problem
  • tile.openstreetmap.org is your default basemap. OSMF's policy says access may be withdrawn without notice and that commercial or heavy use should expect this. Donated infrastructure is serving every visitor of a marketed product.
  • Esri tiles come from a keyless legacy endpoint. That is not the licensed access path. Esri's current model wants an ArcGIS Location Platform account and API key. This affects Satellite, Dark, the dark labels, both game maps and the imagery-date lookup.
  • OSRM demo server is documented as not for production, and routing is a headline feature of your app.
  • OpenTopoMap is a small volunteer project on donated hardware, serving your Terrain basemap directly to every browser.
Where
src/features/map/basemaps.ts:25-34 api/_routes/route.ts:9-11 api/_routes/imagery.ts:27
Fix
Move tiles and geocoding onto a provider you have a relationship with. Stadia Maps covers tiles, Nominatim-compatible geocoding and Valhalla routing with one key, which replaces three of the four above. MapTiler is a good tiles-plus-geocoding alternative. If you want to keep this exact satellite imagery legitimately, get an Esri Location Platform key and enable referrer restrictions. Check current pricing yourself, tiers move.
Rotate?
No, but when you add these keys, restrict them by referrer/domain immediately.

H6Anyone can write your AI assistant's system prompt

Problem
Two separate routes into the same weakness. First, the whole context object from the request body is pasted into the system message with only a size cap, no schema and no validation, so a direct API call can author the assistant's instructions. Second, world-editable OpenStreetMap names and Wikidata labels land in that same block, and your prompt actively tells the model to treat that block as its only source of truth about government officials.
Why it matters
An attacker can neutralise your guardrails and make your branded assistant state anything, on your bill, with your "source: Wikidata" framing around it. Editing a Wikidata label reaches every user who selects that location, with no access to them at all. This is reputational and cost abuse, not a data breach: there are no tools, no database access and no key in the prompt, so nothing privileged can be reached this way.
Where
api/_routes/ai/copilot.ts:15-56,87-118 api/_routes/ai/agent.ts:26-77,99-121
Fix
Move all location data out of the system message into a separate user message, wrapped in delimiters with a line saying it is untrusted retrieved data and must never be treated as instructions. Then validate context against a strict schema: known keys only, enums for status fields, every string capped at ~200 characters with newlines stripped.
Rotate?
No.

M2Your rate-limit database functions can be called by anyone holding a Supabase anon key

Problem
check_rate_limit() and prune_rate_limits() are security definer functions in the public schema. Postgres grants EXECUTE to PUBLIC by default and Supabase exposes them as REST endpoints. There is no revoke anywhere in your migrations.
Why it matters
prune_rate_limits wipes the whole table, resetting the counter that exists specifically to stop someone brute-forcing your admin key. Calling check_rate_limit with a chosen key can lock you out of the endpoint that turns maintenance mode off. Not reachable today, because your frontend embeds no Supabase key at all. It becomes live the moment one is introduced or leaks.
Where
supabase/migrations/0005_rate_limits.sql:36-72
Fix
revoke execute on function public.check_rate_limit(text,integer,integer),
  public.prune_rate_limits() from public, anon, authenticated;
grant execute on function public.check_rate_limit(text,integer,integer),
  public.prune_rate_limits() to service_role;
Rotate?
No.

Verified safewhat I checked and found correctly done

This is not a courtesy list. Each of these is a specific thing I looked for and did not find, or found done properly. Several are the exact places apps like yours usually leak.

No secret reaches the browser. Exactly one VITE_ variable exists, VITE_GTM_ID, which is public by design.

Production bundle is clean. I grepped all 128 built files for JWTs, sk-, AIza, service_role, Bearer tokens and long hex blobs. Zero matches.

No source maps in production. Confirmed live: /assets/index-*.js.map returns 404.

Service-role key cannot reach the frontend. Supabase is imported in exactly one server-side file; src/ has zero Supabase references.

No credentials in git history. There is no history. Nothing was ever committed.

Admin password comparison is constant-time and fails closed when unset.

No XSS anywhere. Zero uses of dangerouslySetInnerHTML, innerHTML, eval or new Function in src/. No markdown or HTML renderer is even installed, so OSM tags, RSS titles and AI output all render as escaped text.

No SSRF. Every outbound URL is a hardcoded host and path. No user value ever becomes a hostname, scheme or full URL.

No SQL or Overpass injection. Every database call is the query builder or a parameterised RPC. No user text ever reaches an Overpass query — only numbers and a whitelisted filter table.

No path traversal. The router matches a static allowlist with Object.hasOwn. I confirmed live that /api/toString returns 404.

No IDOR. No endpoint takes an id or email to fetch or change a specific record.

No CSRF surface. No cookies, no sessions, no CORS headers. The API is same-origin only.

CSP is genuinely strong and confirmed live: no unsafe-inline or unsafe-eval for scripts, with base-uri, form-action, frame-ancestors and object-src all set. A test fails the build if an inline script reappears.

HSTS is fully correct and live: 2 years, includeSubDomains, preload.

Row-level security is on for all six tables with zero policies, which means the anon key reaches no data at all. Deny by default, correct.

All five npm advisories are dev-only and unreachable in the deployed app. Do not run npm audit fix --force; it would install two major versions of Vite and Vitest for no production benefit.

No unused production dependencies. three is not in your project at all — that earlier note was wrong.

Service worker is well built. It refuses to cache /api/ responses and all cross-origin requests, so no personal data or map tile lands in a client cache.

The AI has no tools, no database access and no key in its prompt. User instructions cannot reach anything privileged, and no key can be extracted through it.

Model and token limits are server-side. No caller can pick an expensive model or a huge output.

Precise coordinates are handled carefully. Routes carrying full precision are marked private so they stay out of the shared CDN; everything else is grid-snapped.

No file upload or import exists, so there is nothing to attack there. No user-supplied GeoJSON is ever parsed.

Map styles and tile URLs are hardcoded. Nothing user-controlled can reach a style, source or tile URL.

Attribution mechanism is policy-compliant on the Standard basemap: it shows expanded on load and collapses to an ⓘ on interaction, which is exactly what the guidelines allow.

No scraping or bulk downloading anywhere. Overpass queries are bounded and the Overpass mirror hedging is better engineering than most projects manage.

Every outbound call has a timeout (one exception, imagery.ts:124).

No debug or test routes in production. /api/health returns only a status and timestamp. Dev middleware cannot ship. Zero console.log in the whole project.

/.env, /.git/config, /package.json return 200 but they are your app's HTML page, not the files. I fetched each one and verified the body. Nothing is exposed.

robots.txt correctly disallows /admin, and the admin surface is protected server-side rather than by robots.txt.

Authenticationsection 12 of your brief

There is no user authentication in this application. No accounts, no login, no passwords, no OAuth, no password reset, no email verification, no sessions and no cookies. So account takeover, session expiry, cookie flags, brute-force protection and account enumeration do not apply — with one exception, which is the single shared admin password covered in C1. That is your entire authentication surface, and it is the most serious finding in this report.

Limitations of this audit

I did not open your .env.local. Everything about your secrets is inferred from how the code uses them and from what is or is not in the built bundle. I cannot confirm the values are strong, or that the same value is not reused elsewhere. In particular I cannot tell you how long or random your admin key is, which is the difference between C1 being serious and being catastrophic.

I could not inspect your Vercel or Supabase dashboards. Migration files say row-level security is enabled on all six tables. That is what the files say, not what the live database does. Confirm in the Supabase dashboard that RLS is on for all six and that no policy was added by hand. Also confirm which environment variables are actually set in Vercel production, and that PUBLIC_APP_URL is among them.

I only tested safely and non-destructively. I sent one deliberately wrong admin key to confirm the oracle exists. I did not attempt to guess the real one, did not load-test your endpoints, and did not send anything to third-party services beyond normal use.

A code audit cannot see runtime behaviour. I cannot see your actual traffic, whether anyone has already abused these endpoints, what is in your logs, or whether your Supabase data has been accessed. If you want to know whether C1 has already been exploited, check Vercel's logs for repeated requests to /api/admin/*.

This is one pass by one reviewer. Finding nothing in a category means I did not find it, not that it is not there. Nothing here replaces a professional penetration test if this app ever handles anything more sensitive than it does today.
